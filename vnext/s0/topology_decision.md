# S0 — выбор компоновки по проверенным сценариям

**Статус: IN_PROGRESS / решение НЕ ПРИНЯТО.** Нормативное ТЗ —
[#569](https://github.com/iamaman11/okx/issues/569), схемы владельцев —
[#571](https://github.com/iamaman11/okx/issues/571)–[#574](https://github.com/iamaman11/okx/issues/574).
Этот документ не разрешает торговлю, миграцию финансового SQLite, установку или
перезапуск действующего Engine.

## Что сравниваем

| Владелец | Компактная топология | Разделённая топология | Инвариант в обеих |
| --- | --- | --- | --- |
| Engine | `risk` + `trade-execution` вместе с типизированным входом (2 crates) | `risk` + `trade-execution` + отдельный `trading-engine` (3 crates) | Только один финансовый writer; тот же SQLite/WAL/RiskBook; `Prepared` не является правом POST |
| Research | Replay/HTTP и численное ядро в одном Cargo package | Отдельный `strategy-core` и Replay/HTTP package | Тот же causal replay, единицы измерения, численные результаты и отказ на future leak |

Во всех вариантах **четыре приложения** остаются физически самостоятельными
`vnext/{engine,research,control,edge}`. Внутреннее количество Rust crates не
равно количеству процессов или выпускаемых приложений. Control и Edge в этом
сравнении не получают новых процессов, БД или универсальных IPC-обвязок.

Временный compact-экспорт перемещает **те же существующие исходники**, а не
создаёт вторую нормативную реализацию. Экспериментальная копия никогда не
устанавливается и удаляется после измерения; в Git хранится только её
воспроизводимый рецепт.

## Обязательные сценарии и оракулы

1. **Engine/SQLite:** типизированная ручная команда → реальный SQLite/WAL
   `PREPARED` → повторный вызов и reopen; отдельно штатные проверенные
   `UnifiedFinanceHandle`/`CommittedVenueSend` свидетели reserve, commit,
   потерянного ответа и **ровно одной имитации отправки**. Пока эти два тестовых
   участка не соединены новым production handler, полного end-to-end торгового
   маршрута **нет**. Отдельная `--probe finance` запускает red/green
   oracle на подлинном SQLite `PREPARE`, затем переизмеряет оба графа после
   изменения только финансового исходника; итоговые времена ещё не получены.
   Ни один mock не выдаёт право Real trading.
2. **Research:** три QueryPlan A/B/C по одним шести неизменным закрытым свечам
   вычисляют ожидаемые численные ряды в обоих графах (конечные значения
   16,5 / 15 / 10,5). Один и тот же source digest, разные планы, повторный
   детерминированный replay; внешний MCP/API ещё не реализован.
   Негативные случаи — заглядывание в будущее,
   дубли, пропуск бара, лишнее поле входящего JSON.
3. **Изменения исходников:** для Engine — типизированный command-only diff и
   отдельно finance/SQL-only diff; для Research — kernel-only и
   HTTP-adapter-only diff. Результаты для одного класса нельзя переносить на
   другой.
4. **Независимость:** каждый корень собран без исходников соседей. Факты
   старого приложения и все оставшиеся пользовательские сценарии перечислены
   в [functional_coverage.md](functional_coverage.md), а смешанные источники —
   в [split-symbols.tsv](../split-symbols.tsv).

## Как выбираем

| Критерий | Необходимое доказательство | Пока |
| --- | --- | --- |
| Эквивалентность | Оба варианта проходят одни и те же финансовые/численные позитивные и негативные оракулы | Частично: отдельные исполнимые тесты; требуется объединённый E2E |
| Инвалидация Cargo | Сопоставимые реальные source diff, rustc/rustdoc invocations, nonfresh artifacts, отдельное наблюдение линковки или честный `unknown` | Не завершено |
| Время | Cold/warm, p50/p95/max, очередь, точные compiler/test events, критический путь protected gate | Не доказано |
| Сложность | Количество owner crates, зависимостей, путей установки, нормативных реализаций, migration cutpoints | Нужна оценка после измерений |
| Безопасность | Один writer, ACK/UNKNOWN/POST-once, защита без Research, OS/финансовые свидетели | Только часть сохранённых локальных witnesses |
| Выпуск | Независимые immutable artifacts, проверка версий, install/rollback без пересборки или остановки другого приложения | Не реализовано в новом продукте |

Нельзя выбирать победителя лишь по «crates стало меньше» или одному прогону.
Прогретый Ready-цикл **≤120 секунд** включает обязательную применимую
финансовую/OS-проверку и выпуск артефакта. Локальное измерение ниже этого
порога не считается PASS без точного CI SHA/tree и полной матрицы.

## Уже полученный baseline — не A/B

В первом успешном изолированном GitHub CI срезе
[`6801860a`](https://github.com/iamaman11/okx/commit/6801860a3a4b0e9a83a44ebe01d0d03a21f2a5a7)
журналы [Engine](https://github.com/iamaman11/okx/actions/runs/45335234218)
и [Research](https://github.com/iamaman11/okx/actions/runs/45335234151)
показывают соответственно Clippy **34,13 / 30,24 с**, тестовую сборку
**25,70 / 21,01 с**, release-сборку **73 / 43,84 с**. У Engine дополнительно
около 17 секунд выполняются финансовые тесты. Это один холодный/неразмеченный
по прогреву CI run каждого владельца, **не** сопоставимые две топологии и
**не** измеренный защищённый цикл ≤120 секунд.

## Локальный Engine A/B — первый измеренный исход

Воспроизводимый рецепт — [engine_topology_ab.py](engine_topology_ab.py),
сырой образец — [engine_ab_local_sample.json](engine_ab_local_sample.json).
Два изолированных Cargo target, один и тот же pinned financial source и
одинаковое **изменение рабочего кода** валидации идентификатора (запрет
terminal dot) с новым негативным тестом:

| Операция (одна локальная проба, Linux) | Compact, 2 crates | Split, 3 crates |
| --- | ---: | ---: |
| Первоначальная тестовая сборка/выбранный SQLite oracle | 19,193 с | 18,033 с |
| Первоначальная release-сборка | 46,539 с | 47,413 с |
| Пересборка теста после command-only diff | 3,604 с | 0,447 с |
| Release-пересборка после diff | 11,623 с | 0,964 с |
| Наблюдённые Cargo-started `rustc` после diff (test / release) | 3 / 1 | 3 / 1 |

Оба варианта выполнили одинаковый настоящий SQLite/WAL handoff и два
`CommittedVenueSend::send` fake-venue lost-ACK/POST-once свидетеля. Этот
результат поддерживает **гипотезу** о выгоде отдельного лёгкого command
crate для изменений входа: количество `rustc` одинаково, но compact
перекомпилирует тяжёлое финансовое содержимое. Однако один прогон, один
тип diff и `rustc` counts без фактических linker-subprocess events не являются
основанием для окончательного архитектурного решения. Finance-only diff,
Windows, p50/p95 и готовый production E2E всё ещё **OPEN**.

## Локальный Research A/B — два разных класса изменения

Исходные результаты — [research_ab_local_sample.json](research_ab_local_sample.json),
рецепт экспорта — [research_topology.py](research_topology.py),
проверка численного результата — [research_oracle.py](research_oracle.py),
пинованные source probes — [research_diff.py](research_diff.py).
Оба графа выполнили тот же replay со значениями rolling mean
`[null, 3.0]` и четыре отрицательных проверки. Временные пробы меняли
реальные константы source-файлов **только в копиях**; они не являются
доработкой производственного алгоритма или проверкой новой политики лимита.

| Пересборка после изменения (один локальный Linux-прогон) | Compact, 1 crate | Split, 2 crates |
| --- | ---: | ---: |
| Kernel-only: тесты / release | 0,741 / 1,562 с | 0,721 / 2,502 с |
| Kernel-only: `rustc` для тестов / release | 2 / 1 | 5 / 2 |
| HTTP-adapter-only: тесты / release | 0,678 / 1,510 с | 0,475 / 1,095 с |
| HTTP-adapter-only: `rustc` для тестов / release | 2 / 1 | 2 / 1 |

В одной пробе выиграл compact, в другой split. Все измеренные тёплые
длительности малы относительно обязательного полного CI; поэтому на
основании этой пары нельзя утверждать, что добавление отдельного Research
crate само по себе ускоряет выпуск. Изоляция чистого численного ядра от
HTTP/TLS и простой путь расширения остаются самостоятельными критериями.
Нужны повторения, Windows, фактические linker events/артефакты и сценарий
нового оператора/источника, а не только временное изменение константы.

## Следующий проверяемый исход — расширенные S0-пробы (ещё не PASS)

- `engine_topology_ab.py --probe finance`: новая самостоятельная пара
  compact/split на реальном коде `AccountStore::prepare_sql_transaction`.
  Временное изменение отвергает idempotency key с terminal dot; его
  отрицательный oracle сначала обязан **упасть** без изменения production
  кода. Затем обе компоновки должны пройти SQLite reopen и отдельные
  fake-venue send-once/LOST ACK witnesses до и после изменения. Нужны реальные
  Cargo compiler/link/test события и измерения, поэтому числового результата
  пока нет. Сам финансовый код в `vnext/engine` не изменяется.
- `research_oracle.py`: A/B/C на одном immutable source, отдельные ожидаемые
  полные ряды и source SHA-256; новые позитивные сценарии находятся также в
  обязательном standalone Research CLI integration test. До CI PASS и запуска
  обоих экспортов на конкретном SHA результат не объявляется доказанным.

## Решение и следующий физический эксперимент

- **Сохранить текущие split-границы как рабочий baseline** до окончания
  сопоставимых изменений в обоих графах; compact — измеряемый кандидат, не
  утверждённая архитектура.
- Для каждого варианта публиковать immutable source/manifest fingerprint,
  host/toolchain, одинаковый diff, тестовый oracle, rustc и build events,
  длительности и ограничения. Команды — в `engine_topology_ab.py`,
  `research_topology.py`, `research_oracle.py` и измерителе `measure.py`.
- Затем прогнать те же representative diffs на Windows/Linux с пригодной
  дисковой ёмкостью и одинаковой политикой cache. Пробу с `SQLITE_FULL` или
  переполненным временным каталогом отклонить как **несопоставимую**.
- После полного финансового HTTP-emulator/OS и исследовательского E2E
  подтвердить разделение, contract/diagnostic/install/rollback, только затем
  закрывать S0 и выбирать окончательную топологию.
