# Architecture contract: clean Engine (#398)

The canonical specification is [#398](https://github.com/iamaman11/okx/issues/398). This document describes its implemented boundaries; code/fixture success and installed exchange acceptance are separate evidence. The [former contract](history/ARCHITECTURE_CONTRACT_V1-before-398.md) is historical and imposes no migration or activation gate.

One Rust Engine owns independent account contexts. AccountKey is venue + environment + authenticated UID fingerprint. An immutable alias/credential-reference catalog routes explicit commands; changing an operator view cannot redirect an existing intent. Accounts have separate SQL actors, private sources, mutation queues and canonical writer leases. An unavailable account does not hold another account's queue.

Each account has one addressed WAL SQLite owner, [account-v2.sql](../crates/okx-execution/schema/account-v2.sql). Immutable decisions/plans, facts, source cursors and projections commit transactionally. Queries use keys, indexes and bounded pages; terminal history is not reconstructed into a second RAM ledger. Opening T0 is initialized explicitly from verified current flat exchange evidence. Missing/corrupt ordinary storage is an error, never an implicit empty database. No previous financial formats are read or imported.

Manual commands and automatic StrategyKernel decisions enter the same native TradeService. Begin-post commits exactly once before a gateway invocation. An uncertain outcome becomes UNKNOWN and is read back by exact client identity, never resubmitted. Filled quantity retains instance ownership and central occupancy until the exact owned exposure is closed. Attached protection is verified from the exchange; failure enters STOP and the owned compensation path. Strategy parameter updates append immutable SQL versions; intents keep their original definition binding.

The existing Cloudflare Durable Object owns persistent account access, transactional revisions and one indexed central RiskBook. Admission consumes a complete fresh census of registered Real accounts. Paused accounts remain in that census. The USD10 campaign consumes actual loss plus costs cumulatively across accounts/strategies/restarts/dates; profits do not refill it. An owner may only lower the ceiling atomically, never reset risk or raise it. Native current-source, ownership, financial and protection checks remain mandatory before POST. Closing/reconciliation can continue under pause or exhausted new-risk budget when ownership is proven.

The public surface is seven strict tools: accounts, strategies, market, research, trade, portfolio, diagnostics. One authenticated WSS carries generation-bound requests, ACKs, responses, policy pushes and addressed risk requests. Unknown installation/contract/session generation is rejected. GitHub encrypted DATA is read-only diagnostic transport; issue12 CONTROL is the existing typed lifecycle/install transport. There is no mutation fallback through GitHub.

Analytics compose shared closed-bar sources/cache and pure Rust operators on the existing bounded CPU executor. Live/replay share causal strategy kernels. Jobs, immutable artifacts and bounded instrument/trade pages survive restart; a batch reports independent instrument results rather than inventing portfolio returns. SQL ownership, venue gateways and CONTROL do not change when a pure metric or strategy variant is added.

CONTROL and the verified launcher/controller/agent ReleaseSet own process lifecycle, Jobs, autostart, explicit clean initialization and new-format backup/restore. They do not own trading grants or financial policy. Ordinary restart retains new-format state and saved access. Restore uses a bounded historical audit and fresh exchange/central reconciliation before clearing its storage gate. Shutdown drains and preserves uncertainty; it does not automatically close exposure.

Defaults, transition table, queues, TTL, retention and operational steps are in [Product acceptance](PRODUCT_ACCEPTANCE.md). [Roadmap](ROADMAP.md) reports published checkpoints. Final physical results are recorded against the exact GitHub release; a successful build or promotion is not a physical PASS.
